# Backend load test: saving after a raid

The heaviest thing a player does to the backend is leaving a raid. The client saves the whole profile
(stash, gear, quests, hideout) with `PUT /api/v1/profile` (compare-and-swap on the revision), records the
raid with `POST /api/v1/raids`, and sometimes opens the leaderboard. `server/cmd/loadtest` does exactly
that in a closed loop with **no think time**, so the numbers are the server's ceiling, not a realistic
load. A real player saves this way once every 10–30 minutes, so 400 saves/s is roughly what 150,000+
players finishing raids continuously would produce.

## Setup

- The image from `server/Dockerfile`: the API and MongoDB 8.0 in the same container, data on a Docker
  volume, `j: true` writes for player data.
- Profile: a real one generated by the engine with a full stash (121 items), 10.3 KB of JSON. A second
  run pads it to 110 KB to stand in for a hoarder.
- Each step runs for 20 s. Accounts are created before the measurement.
- The 4-vCPU runs share the machine with the load generator, which takes about 0.8 of a core.

### Railway, live (`ashfall-api-production.up.railway.app`, 30 Oct 2026)

The same image on Railway (one service, MongoDB inside, data on a Railway Volume at `/data/db`), run
from a home connection with `-steps 10,50 -dur 15s` so as not to disturb the live server.
`REGISTER_PER_HOUR` was raised for the run and removed afterwards. Client-side numbers include the
round trip over the internet; "server p95/p99" are Railway's own HTTP metrics for the same window.

| Players at once | Profile | Saves/s | Save p50 | p95    | p99    | Errors |
| --------------- | ------- | ------- | -------- | ------ | ------ | ------ |
| 10              | 0.1 KB  | 43      | 104 ms   | 139 ms | 330 ms | 0      |
| 50              | 0.1 KB  | 201     | 109 ms   | 167 ms | 354 ms | 0      |
| 10              | 10 KB   | 15      | 184 ms   | 1.3 s  | 4.3 s  | 0      |
| 50              | 10 KB   | 22      | 1.1 s    | 2.4 s  | 2.6 s  | 0      |

| Endpoint, measured by Railway | Requests | p50   | p95   | p99    |
| ----------------------------- | -------- | ----- | ----- | ------ |
| `PUT /api/v1/profile`         | 4.3K     | 29 ms | 67 ms | 151 ms |
| `POST /api/v1/raids`          | 4.3K     | 5 ms  | 10 ms | 25 ms  |
| `GET /api/v1/leaderboard`     | 457      | 1 ms  | 8 ms  | 8 ms   |

CPU peaked at 0.28 vCPU and memory at 300 MB (the plan allows 8 vCPU / 8 GB). 0 acknowledged saves
lost.

**Reading it:** the server was nowhere near its limit. With 10 KB profiles the client's upload link
was the bottleneck (about 220 KB/s of saves), which is where the seconds of latency come from; the
server itself answered saves in 67 ms at p95. The capacity numbers above (local, 1 vCPU) remain the
ones to plan with; this run shows the deployed stack (proxy, volume, journaled writes) adds no errors.

**Reading it:** no request failed at any level, including 1000 players saving at the same moment on
one core. Past saturation the server queues instead of failing, so only latency grows (linearly with
the queue). The client saves in the background with an 8 s timeout, so even 2–3 s at p99 is invisible
in play.

## What the test changed

| Change                                                                                     | Effect                                                                     |
| ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| Cache token → player for 60 s in the API (auth no longer reads the database on every call) | 830 → 1236 saves/s at 1000 players, p95 −20%                               |
| Cache the leaderboard for 5 s                                                              | leaderboard p50 250 ms → 16 ms under load                                  |
| `j: true` writes for profiles, players and raids                                           | −8% at saturation; a save acknowledged to the client survives a host crash |
| Rate limit uses the last `X-Forwarded-For` hop (the one the proxy adds)                    | the first hop is client-supplied and could be forged to dodge the limits   |
| Client: on 409 the newer of local and server copies wins                                   | before, a lost reply made the client discard a newer local profile         |

## Crash test

250 players saving continuously; the container was killed with `SIGKILL` 12 s in, then started again.

- Back up and healthy in 4 s (MongoDB replayed its journal).
- 0 corrupted profiles (every stored profile parses and has a revision).
- 0 acknowledged saves lost (the test counts any 409 that reports an older revision than one the
  server had already confirmed).
- About 80 saves came back 409 right after the restart: those were applied just before the kill but
  their replies never arrived. The client resolves it by keeping the newer copy.

## Run it

```bash
docker compose up --build
```

```bash
cd server && go run ./cmd/loadtest -url http://localhost:8080 -steps 25,100,250 -dur 20s
```

`-profile file.json` sends a real profile (export one from the browser's IndexedDB), `-pad 100` adds
100 KB to it. The API allows 10 new accounts per IP per hour; for a test with more players start it
with `REGISTER_PER_HOUR=100000`.
